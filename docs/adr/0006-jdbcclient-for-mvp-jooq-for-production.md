# JdbcClient with hand-written SQL for the MVP, jOOQ for production, not JPA

Persistence stays on Spring's `JdbcClient` with hand-written SQL for the MVP; the recommended production path is jOOQ with code generated from the Flyway migrations. JPA is rejected because the schema fits it badly. The next Turn ordinal and Source Version number are computed inside the INSERT, and a Passage's search vector is computed at insert from its Source's labels. Registering a Source is an upsert on its registry key, and retiring Sources is an `UPDATE … RETURNING` with a subquery. Columns use Postgres `text[]`, `vector` and `tsvector`, and most reads are projections such as Citation snapshots rather than entity graphs. The result would be a JPA + native-query hybrid with string queries anyway: two models and still no compile-time safety. Spring Data JDBC is rejected because, although it maps the aggregates (Conversation → Turn → Citation, Source → Source Version → Passage), its queries stay strings, so it adds no safety over `JdbcClient`. jOOQ is preferred for production because generated table and column symbols turn schema drift into compile errors while keeping full Postgres SQL (`ON CONFLICT`, `RETURNING`, arrays, custom operators).

Retrieval stays native SQL whichever option is used (ADR-0005). For the MVP the missing compile-time checks are accepted because the HTTP-level integration tests run every statement against real Postgres with pgvector on every build, so a typo or a missing parameter fails the build rather than production.
